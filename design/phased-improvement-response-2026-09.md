## 二、落地方案：按报告「下一轮 10 项」的顺序，合成四个工作节点

每个节点 = 代码 + 守卫 + 部署 + 四个测试号在生产上核对（做法不变）。节点之间连续推进：一个节点上线并核对完即进入下一个，不按天计。

### 节点 1 · 可信（报告 1 · 3 · 4）

**1 一个事实源 + 状态推导**
- 扩 `lifecycle_facts_tenant()` / `lifecycle_facts_landlord()`（已有，SECURITY INVOKER），新增 `lifecycle_facts_agent()` / `lifecycle_facts_provider()`；一次返回瓦片 / 看板 / 今日卡 / rail / 我的租金 / 我的申请 / 待批 需要的全部事实。
  客户端 `lib/facts/useFacts.ts`：每页一次取数、2 秒共享缓存、变更事件刷新。
- `lib/matters/states.ts`：房源 / 申请 / 筛查 / 租约 / 报修工单 / 服务工单六张状态表 + 中英标签 + **按日期推导的展示态**——
  租约按报告建议：草稿 → 待签署 → **已签待生效** → 生效中 → 已结束；`signed_both` 且 `start_date > today` 永远不是「生效中」。
- 改读事实源：`StatusOverview`、`LiveMaintenanceBoard` 计数、`MyRent`、`MyApplications`、`TodayCard`、`LifecycleRail`、`/landlord/leases`、`/listings` 计数；
  守卫：这些组件不得再直接查 `lease_documents` / `maintenance_tickets` / `rent_payments` / `applications`。
- `/listings`：一个数 + 「按档案筛后 N / 共 M」说明；`/api/public/stats` 与页面用同一谓词（可见 + 有照片）。
- **4 租约状态机的连带**：`proactive`（续约 90/60/30、催租、relist、邀请提醒）与 StatusOverview 的续约窗口只看 `start_date <= today` 的租约；租金记录不会对未起租的租约生成提醒。
- 验收（对应报告阶段 01 的指标）：固定测试数据在所有入口的状态与计数一致（脚本跨页比对）；未起租租约任何页面都不显示生效中。

**3 预算硬约束**
- 清掉 13 行可见房源上残留的 `badge` / `match_score` / `luna_note`（只有 8 Colvestone 有值），`/listings` 不再渲染、不再按它排序；
  三列保留在表里但守卫禁止任何页面读取（等有真实的档案匹配再决定要不要算）。
- `lib/agent/hardConstraints.ts`（纯函数）：从**当前消息 + 记忆**推导预算 / 户型 / 入住日 / 宠物 / 区域，与模型的 `search` 合并——模型只能收紧不能放宽；
  超预算的一律不进正常推荐，回复末尾由系统写「按预算 ≤ $2,800 过滤；另有 N 套超预算未列，要看就说」；「换一批」沿用；记忆预算与这句话冲突先问。
- 验收：夹具「记忆有预算、消息没提」→ 结果全部 ≤ 预算；`/listings` 对已登录租客按档案筛时超预算的行标「超预算」而不是排前面。

### 节点 2 · 清楚（报告 2 · 5 · 6 · 10）

**2 服务商角色入口**
- `provider` 成为第四顶可落地的帽子：`homeForHats` / `activeHat` / `heldHat` 认识它；登录落点 = 最后一次明确选择的、且仍持有的身份；只有一顶非租客身份时直接进它的工作台（纯服务商号 → `/provider/jobs`）。
- `useAuth().role` 的出口一律经 `activeHat`（`/notifications` 等页不再拿到未持有的帽子）；「记住上次身份」只记持有的帽子；跨身份深链先提示「切换后继续」，不静默穿越。
- 通知中心按当前身份加载；服务商的通知（新工单 / 报价被批准 / 验收 / 争议）落到 `/provider/jobs` 而不是房东页。
- 顶部常驻「当前身份」在工作台 app 壳里（见 10）。

**5 经纪授权模型：现在「禁止」，Phase 3「委托进入」**
- 删 agent-test 误开通的房东行；「开通身份」三处（claim_landlord / 经纪认证 / 服务商入驻）一律写审计（谁、何时、从哪个入口）。
- 守卫 + `route-audit` 探针：无房东帽子的账号访问 `/landlord/*` 被送去开通页，且房东数据接口对它返回空（RLS）；服务商读不到他人 household；租客读不到工单 token。
- 审计字段补齐（报告第 11 页最小字段）：`agent_audit_events` 加 `acting_role`、`matter_ref`（household / application / lease / work_order 之一）、`delegation_id`（先为空）；
  执行路由与 orchestrator 写入时带上；活动面板与审计页显示「以什么身份」。
- 委托模型（委托人 / 受托人 / 范围 / 期限 / 依据 / 撤销）放节点 5。

**6 补关键任务入口**
- 租客申请详情页 `/tenant/applications/[id]`：材料清单与缺项、状态时间线（提交 → 房东已查看 → 筛查已发起 → 决定 → 租约）、下一步与责任方（房东 / 你）、对应的看房与提问；**不显示分数**（守卫已有）。
- 经纪待办：`clientTasks()`（缺代表协议 / Information Guide 日期、7 天未联系、看房中备包、已申请跟进）+ RECO 到期 ≤30 天 并入经纪的今日卡与 `/agent/todo`；空态说明怎么开始。
- 房东归档：独立归档表（按房源分组、可搜索）+ 「后续」列（决定通知发了没、是否已签约、是否已入住）+ 逐条恢复。
- 「租客筛查」导航对租客帽子：/screening 的 CTA 分流——租客看到「筛查是房东的功能。你可以先备好租客护照与材料包」（链到护照 / 申请），房东与经纪照旧进 `/screening/app`。

**10 文案与可访问性清理**
- `/apply` 宠物 / 吸烟改「否 / 是」；Brief 三处改助手名 / 「带看准备包」；经纪设置页显示「经纪档即将推出 · 现在免费」。
- 「非中文字符串」守卫：登录后页面与筛查流程里面向用户的固定文案不得含未翻译英文（白名单：专有名词、法条编号、MLS® 等）。

### 节点 3 · 可执行（报告 7 · 8）

**7 服务商经营视图**

### 节点 4 · 连贯（报告 9）

**9 消息 thread 最小版**
- 通用线程 `threads(kind: work_order | application | tenancy | dispute, ref_id)` + `thread_messages`：**只追加**（无 update / delete 策略；撤回 = 新增一条引用原消息的「撤回」记录）、服务器时间 + 按用户时区显示、发送者 `acting_role` 快照、`message_reads`（送达 / 打开 / 确认三态）、附件走现有桶并记 SHA-256、查看 / 下载写访问审计。
- 先做维修三方线程（租客 · 房东 · 服务商，接进 `/h/[id]` 报修标签、`/provider/jobs`、`/w/[token]`），再把 `household_messages` 迁成租约线程；申请线程随二-6 的申请详情页。
- 通知只做提醒；正式通知（决定通知 / 续约函 / 进入通知）仍是独立执行器 + 邮件，在线程里留「正式通知」副本并明写「不构成 RTA 法定送达」。
- 验收 = 报告第 21 页的演示脚本：服务商登录进正确工作台 → 租客报修、房东派单 → 服务商收到通知进入三方线程 → 报价、房东确认、各角色状态一致 → 导出含身份 / 时间 / 附件校验的记录（导出放节点 6）。

### 节点 5 · 租赁事务主记录与经纪委托（报告 31–60 天段）
- 租赁事务主记录 `rental_matters`：把房源 / 申请 / 租约 / 付款 / 工单 / 线程 / 文件挂到一个 `matter_id`；页面、通知、导出与审计都带它；`/x/progress` 变成事务页。
- 角色档案与委托：`delegations`（委托人 / 受托人 / 范围：房源 · 找房 · 事务 / 允许动作 / 期限 / 撤销 / 依据版本），客户经邮件链接确认；经纪的页面常驻「正在代表：某房东 · 范围 · 到期」；代客筛查在有效委托下开放；撤销即时失效并审计。
- 维修全套动作（接单 / 报价 / 改期 / 到场 / 变更 / 完工 / 验收）从卡片直接完成并回写。

### 节点 6 · 可收口（报告 61–90 天段）
- 账单与线下结算回执、评价与历史工单（节点 3 已做大半）；消息时间线 + PDF 证据包导出 + 访问审计；正式通知分流与 CASL（等真有营销邮件再做同意管理）。
- 保险 / 法律服务商类型：等资质规则（FSRA / LSO）与合规形态明确后再开。
