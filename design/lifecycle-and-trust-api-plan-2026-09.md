# 租房全流程 AI 与 Trust API 优化方案（2026-09-22）

依据：`~/Downloads/eliseai-story-and-site-analysis.pdf`（EliseAI 故事与网站结构分析，18 页）+ 2026-09-22 生产库实数 + 现有代码盘点。
报告对 Stayloop 的核心判断只有一句：**复制闭环方法，不复制企业级外观**——"为安省小房东、经纪与租客设计的可审计租赁操作系统"。
本方案把这句话落到我们已有的模块上：哪些优点要加固，哪些环节要接通，Trust API 应该变成什么。

**优化方案的第一原则：先把筛查这个优点做成别人抄不走的，再用它把前后两环（申请、签约）拉起来，而不是平铺十个环节。**

## 1. 要加固的优点（这是我们的护城河，报告说的"更本地、更轻量、更可审计"）

| 优点 | 今天已经做到 | 加固动作 |
|---|---|---|
| **确定性核验层**——评分不出自模型之口 | 工资单算术、征信转录 + 分析、跨文档互证、取证（Producer / 生成器指纹 / 增量更新）、LTB 目录、法院门户当事人检索、雇主注册 + Gazette + RDAP + Bank Act、租金押金合法性 | ① 把每条确定性规则**编号并公开**（`/screening/rules`：规则 → 依据法条 / 数据源 → 触发条件），报告里每条标记链到规则号。这是 EliseAI 做不到的"可审计"；② 每周把生产上模型输出与确定性层的分歧率写进 `/admin/usage`（模型说矛盾、规则说不是的比例），作为模型槽位选型依据 |
| **安省法规编码进每一步** | OHRC 不设收入截止线、RTA s.106 押金、s.134 禁收费、s.10(7) 通知信、TRESA s.32 披露、O. Reg. 9/18 标准租约 | 抽成一个 `lib/ontario/rules.ts` 单一来源（条文号 + 生效日 + 适用判断函数），guardrail / 房源发布检查 / 租约生成 / 通知信全部引用它；条文变更只改一处 |
| **三角色利益隔离** | 三个助手、三套提示词、帽子与数据归属分离、经纪不得代客筛查 | 写成产品承诺放在 `/trust-api` 与隐私页："租客助手永远不会替房东评分；房东助手永远看不到租客的对话"——并加守卫测试证明（提示词 / 路由层面） |
| **提议 → 确认 → 执行 → 审计 脊柱** | `agent_pending_actions` + `execute` 执行器 + `agent_audit_events`，卡片写明「会用 / 不会用什么数据」 | 补三样：**执行预览**（发信前看到最终邮件正文）、**撤销窗口**（发送类动作批准后 60 秒内可撤）、**执行回执**进活动日志（已做）。报告第 7 条"借鉴 Apollo 但必须加权限可见、预览、撤销、审计"——我们缺的只有预览和撤销 |
| **数据来源可指回** | `/partners` 数据来源目录、报告逐条引用文件行、数据库驻加 | 报告每一节加"来源"脚注（已部分），LTB / 法院行加检索时间戳 |
| **手机端 + 主动推送** | 5 项底栏、审批进对话、Web Push 三档 | 无需再做，转为衡量：推送后 24h 内批准率 |

## 2. 租房全流程 AI：按阶段的优化方案

原则：**每一阶段 = 一个真实的数据写入 + 一个助手提议 + 一次人的确认 + 一条审计**。没有数据写入的阶段不做"AI 功能"。

### 2.1 90 天闭环（报告的优先动作）：发布 → 申请 → 筛查 → 决定 → 签约

这条链上每一段今天都有代码，缺的是**段与段之间的接头**。P0 全部是接头工程，不是新模块。

| 段 | 现状 | 接头（P0） | AI 提议 / 人确认 |
|---|---|---|---|
| 发布 | 向导 + 对话发房源，`pending` 待管理员核验 | 无 | 助手补字段、检查押金 / 禁宠；发布由房东点 |
| 申请到达 | `/apply/[slug]` 写 `applications` + 文件；邮件 + 推送给房东 | **申请 → 一键筛查**：房东在申请人页点「筛查」，`applications.files` 直接作为 `screenings.files`，申请表字段预填（姓名 / 租金 / 入住日），不再要求重新上传 | 助手提议「3 份新申请，先筛查材料最全的一份？」；房东点 |
| 筛查 | 227 份，完整 | 无（见 §1 加固） | 已是"仅供参考、非拒绝依据" |
| **决定与通知** | 报告有申请人通知信（打印），**没有发送动作** | 新执行器 `send_decision`：房东在申请人页选「录取 / 婉拒 / 待补材料」→ 助手生成通知（含 s.10(7) 与 OHRC 声明）→ 卡片预览 → 批准后发邮件给申请人，`applications.status` 同步 | 助手起草，**决定与措辞由房东确认**；婉拒信永不写受保护特征（guardrail 已有规则） |
| 签约 | `/landlord/leases/new` + e-sign | **从申请生成租约**：录取后一键带入申请人姓名 / 邮箱 / 租金 / 入住日 / 押金（≤ 一个月）生成草稿；`send_lease` 已在提示词里但**没有执行器**——补上（复用 `/api/lease/send` 的归属校验） | 助手起草条款 + 附表 B 合法性检查；房东确认发出 |
| 双签后 | 无自动动作 | 双方签完 → 自动建 `households`（verified，因双签）+ `rent_payments` 首月应付行 + 续约触点排程（已做）+ 租客侧「入住清单」待办 | 无需确认（这是签约的自然结果），写审计 |

做完这条链，演示可以从"发一套房"讲到"续约信发出"，中间零次跳出产品。

### 2.2 前端（获客与看房）· P1

- **看房意向**已进房东助手（今天上线）。补：租客侧「我的看房」列表（`showing_intents` 本人可读）+ 房东批准后时间协商（两轮邮件即可，不做日历同步）。
- **租客助手找房**是我们比 EliseAI 多的一环（他们服务运营商，不服务找房的人）。加固：搜索结果直接生成「申请材料清单」待办；房源卡「问房东」一键 = 今天的 listing_inquiry。
- **经纪**：认证目录已有；P1 只做「经纪替房东跑筛查前的三前提」硬闸（代表协议记录 + 申请人书面同意勾选），不做代客评分。

### 2.3 入住后（租中）· P2，先量后做

- 报修 / 租金今天是自述数据、0 行。**不建收付通道**（RTA 下小房东多为 e-Transfer），改做「对账」：租客或房东标记已付 → 对方确认 → 双方确认的记录才进租客护照（已有此规则）。助手只做提醒与 N4 说明，不做催收谈判（报告与 Muse 研究均已否决）。
- 报修：保留自述工单 + 助手分诊（紧急 / 非紧急、RTA s.20 房东义务说明）；不派单。

### 2.4 续约与退租 · 已做 / P2

- 90 / 60 / 30 触点已上线，推送已通。P2：租客侧对应触点（N9 60 天提醒、押金利息计算器）。

### 2.5 自然语言操作层（借鉴 Apollo，报告第 7 条）

我们的助手已经是"自然语言入口"。要补齐报告点名的四件事：
1. **权限可见**：卡片的「会用 / 不会用什么数据」已有；加一页 `/x/permissions` 列出助手能读 / 能写的表与执行器（从代码生成，不手写）。
2. **执行预览**：发送类动作（续约信、决定通知、租约、看房回复）批准前展示最终正文。
3. **撤销**：批准后 60 秒延迟执行（`execute` 加 `scheduled_at`），期间可撤；邮件一旦发出不可撤，如实说明。
4. **审计**：已有；补导出（CSV）供房东留档。

### 2.6 五个可证实的 ROI 指标（报告要求"可在试点中被证实"）

全部从现有表算，不需要新埋点；进 `/admin/usage` 与房东「进度」页。

| 指标 | 定义 | 来源 |
|---|---|---|
| 空置天数 | 房源 `created_at` → 该房源租约 `signed_at` | `listings` + `lease_documents.listing_id` |
| 申请周转 | `applications.created_at` → 决定通知发出 | `applications` + `send_decision` 审计事件 |
| 筛查用时 vs 人工 | `screenings.progress` 起止；人工基准取用户实测（Kim-Yi 案人工逐份读 ≈ 2–3 小时） | `screenings` |
| 合规拦截 | guardrail 拦下的输出 + 发布检查 / 租约检查触发次数 | 新增 `compliance_events`（guardrail / 发布向导 / 租约生成各写一行） |
| 续约提前率 | 到期前 ≥90 天收到第一张续约卡的租约占比；30 天内批准率 | `agent_pending_actions.metadata.stage` |

## 3. Trust API 优化方案

### 3.1 现状（如实）

- 文档页写了 `POST /v1/screen`、`POST /v1/passport/verify`、`GET /v1/listings/{id}/compliance`、`POST /v1/disputes/mediate` 与 `api.stayloop.ai`。**没有一个能调用**：域名不存在，`trust_api_keys` 0 行，唯一的路由 `/api/trust/verify` 查的 `rental_passports` 表已不存在。
- 真正存在的"可信事实"有四类：① 本人授权核验快照（Veriff / Flinks / Equifax，`screenings.verification`）；② 双签租约与已确认 household 推出的租史（`/p/<token>` 公开护照页已只认这两种）；③ 筛查报告里的确定性事实（收入算术、证件有效期、LTB / 法院检索结果）；④ 房源合规检查（押金、禁宠、附表 B）。

### 3.2 重新定位：不是"信任 API"，是"安省租房核验 API"

一句话：**申请人本人授权、只返回结论不返回文件、每次调用留痕、法规边界写在响应里。** 这与 EliseAI 无关——它是我们独有的、可以卖给房源平台 / 物业公司 / 经纪公司的东西。

**先划一条法律红线**：向第三方（银行、保险）出售关于个人的核验结论，会把 Stayloop 推向《消费者报告法》的"报告机构"定义。**方案一律限定为"申请人主动出示"模式**：token 由申请人签发、可撤销、有效期 30 天，调用方拿到的是申请人本人授权的结论；面向金融机构的用途在律师意见之前不开。

### 3.3 三个端点，每个都有真实后端

| 端点 | 后端 | 返回 |
|---|---|---|
| `POST /v1/passport/verify` | `passport_share_tokens`（申请人签发）→ `screenings.verification` 快照 + 已确认租史 | `{ identity: verified_at, bank: {payroll_monthly_estimate, nsf_count, sandbox}, credit: {score_band, delinquent}, tenancy: [{months, on_time_ratio}] }`，**不含姓名以外的 PII、不含文件**；每次调用写 `agent_audit_events` 并给申请人推送「X 查看了你的护照」 |
| `POST /v1/screen` | 与站内同一条 `screen-score` 管线，异步 + webhook；调用方必须提交申请人同意记录（consent 版本号 + 时间戳），与站内 `/verify` 同一套同意文本 | `{ screening_id, status }` → webhook `{ score, tier, hard_gates, court_summary, notice_letter_url }`；tier 永远带「非拒绝依据」 |
| `POST /v1/listings/compliance` | 确定性规则（押金 ≤ 1 月、无禁宠条款、无申请费、附表 B 合法性）——`lib/ontario/rules.ts` | `{ passed: bool, findings: [{rule, statute, message}] }`，无 PII，可匿名调用（限流） |

删掉 `disputes/mediate`（无后端、无运营）。

### 3.4 实施步骤

1. **拆掉假的**：文档页只保留三个端点，`api.stayloop.ai` 改为 `www.stayloop.ai/api/v1/…`（同一个 Worker，加路由前缀），删除 "npm SDK"、"20k passports" 等已删文案的残留检查。
2. **密钥与配额**：`trust_api_keys` 已有表（hash 存储、逐键限流 RPC 已有）；后台 `/admin/partners` 发放 / 停用密钥、看调用量。
3. **申请人侧 token**：护照分享页已有 token；加「允许第三方 API 查询」开关与作用域勾选（身份 / 银行 / 征信 / 租史），撤销即 404。
4. **`verify` 端点重写**：改读 `screenings.verification` 与 `/p/<token>` 同一套推导；响应加 `boundary` 字段（不是消费者报告机构、s.10(7) 权利说明）。
5. **`screen` 端点**：包装现有管线 + 同意校验 + webhook；先给一家试点（房源平台或经纪公司）。
6. **`compliance` 端点**：`lib/ontario/rules.ts` 落地后免费开放，作为获客入口（这是最容易被搜索引擎和开发者传播的一个）。
7. **定价**：`screen` 按次（与站内解锁同价 $14.99），`verify` 免费额度 + 按量，`compliance` 免费。
8. **律师意见**：与"消费者报告机构注册"研究合并，结论决定 `verify` 是否对金融机构开放。
