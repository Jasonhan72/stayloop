# 未注册状态下的合规方案（2026-10-12）

前提：s.3 禁止未注册者「conduct or act as a consumer reporting agency」。未注册时合规只有一条路：让 Stayloop 不再是「向房东提供关于申请人的信息」的那一方。
做法是把筛查拆成两种来源、两条通道，并用一个开关 `CRA_MODE = tool | registered` 控制；注册完成后只翻开关。本稿不是法律意见。

## 通道一 · 房东工具模式（房东发起的筛查）

Stayloop 只处理房东已经从申请人那里合法取得的材料，像表格软件一样做分析，不向房东提供任何 Stayloop 自己去找来的、关于申请人本人的信息。

保留（信息来源是申请人交给房东的文件，或关于公司而非自然人）：
- 文件取证（元数据、生成器指纹、排版引擎、篡改痕迹）、跨文件一致性、收入算术、扣缴复算、征信报告转录与分析（申请人自己提供的报告）、时效层。
- 雇主核验里关于**公司**的部分：公司注册库、Ontario Gazette、RDAP 域名、法院门户按**公司名**检索。《消费者报告法》的「consumer」只指自然人。
- 申请人本人授权的 Veriff / Flinks 核验：申请人在自己的同意页上选择把结果交给这位房东（消费者本人书面指示下的披露，s.8(1)(b) 的形态）。这一条仍要律师确认。
- 评分、解读、通知信：都只基于上面这些。

从房东报告里移除（Stayloop 主动检索的、关于申请人本人的记录）：
- 安省法院门户按申请人姓名检索（`runCourtRecordCheck`）。
- LTB 判令目录按申请人姓名检索（`searchLtbOrders`）。
- CanLII 索引检索与预填姓名的人工检索链接（`searchCanliiViaIndex`）。
- 深度核查里按申请人姓名在网上找人（`arm_length_web_index_party_named`）。
- Stayloop API 的 `/v1/screen`（向合作方提供报告，最典型的「furnish」；现在 0 个合作方）。
这些代码不删，按 `CRA_MODE` 关闭，报告里对应位置写「公开记录由申请人自查后提供（见下）」。

## 通道二 · 申请人自查（公开记录与征信）

同一套检索能力改为提供给申请人本人、关于他自己：
- `/verify/<token>` 与租客护照里新增「公开记录自查」：按本人姓名跑法院门户 + LTB 判令目录 + CanLII 索引，结果只给本人看，带日期与签名。
- 申请人决定是否把结果交给房东：最稳的形态是**申请人下载 PDF 后作为申请材料上传**——那就是一份申请人提供的文件，房东报告按文件分析；次稳的形态是申请人在护照里勾选「分享给这位房东」（我们的服务器在申请人指示下向房东显示）。两种形态哪一种可接受，交律师判断；默认先做第一种。
- 征信同理：Equifax 直拉只作为申请人本人拉取自己的报告（消费者本人向 CRA 索取自己的报告是 s.12 的权利），再由申请人提供给房东。这也是安省房东一直以来「请申请人自带征信报告」的做法。
- 房东侧的产品表述：「申请人已附上 N 月 N 日自查的公开记录（由 Stayloop 执行、申请人提供）」；没附的显示「申请人未提供公开记录自查」，不替申请人去查。

## 两条通道都要守的

- 不利信息未经佐证即注明；7 年与 12 个月时效过滤；不含受保护特征。
- s.10(7) 通知信由房东发；申请页同意文本写明材料用途。
- 删除、索取、更正走 V0.8 的 `/my-file` 流程（与注册与否无关，PIPEDA 也要求）。
- 文案不再说「不是报告机构」，也不自称「报告机构」。

## 代价与取舍

- 房东报告失去「替你查法庭与 LTB」这一最有说服力的能力，改为「申请人自查 + 房东可点链接自己去公开门户查」（法院门户与 LTB 开放数据本来就对公众开放，我们只预填检索参数、不读取结果）。
- 转化上要把「申请人自查」做成申请流程的默认一步，否则房东看到的永远是「未提供」。
- 注册成功后翻开关，通道一恢复主动检索，通道二保留为租客的护照能力。

## 工程量
- 开关与门控：1 天（screen-score 四处、deep-check 一处、v1/screen 一处、报告三处的空态文案）。
- 申请人自查页 + PDF：2–3 天（复用现有检索函数与报告渲染）。
- 房东报告的「申请人提供的自查」识别：1 天（文件分类加一类，取证层识别我们自己签发的 PDF 指纹）。
