## 助理回复边生成边显示，对话模型思考档位调低（2026-11-17 夜 · 用户「做流式回复」· ship121–122）

产品报告第 2 条：助理中位 9.4 秒、P90 18 秒，等待时只有一行「思考中」，然后整段一次出来。

**先量清楚时间花在哪**（本机直接调模型，用真实系统提示词）：gemini-3.7-flash 默认档要先「思考」，第一段输出在 7–14 秒才到，之后 3–5 秒写完。所以只做流式的话首字仍要等 10 秒左右。Google 文档：Gemini 3 系列的思考不能关，可以用 `reasoning_effort`（minimal / low / medium / high）调；实测这个模型拒绝 minimal（400），low 档首字 1.6–2.3 秒、整段 4–6 秒。五道代表题（报修出卡、涨租合法性、欠租能否换锁、发布房源出草稿、押金上限）两档各跑一遍，涨租那题两档又各多跑几遍：JSON 都合法、卡片与草稿字段一致、答案实质内容相当，没有看出 low 更差。

**做法**
- **思考档位**：`TURN_REASONING_EFFORT = 'low'`（`app/api/agent/turn/route.ts`）。`lib/llmChat.ts` 新增 `reasoningEffort`，只对 Gemini 的 OpenAI 兼容端点发 `reasoning_effort`（`isGeminiEndpoint`），其他厂商不发。模型不接受时返回 400，`callTurnModel` 去掉参数再试一次。流式与非流式都生效。
- **服务端流式**：请求体带 `stream: true` 才流式；否则还是「空白心跳 + 一个 JSON」，旧页面不受影响。流式时每行一个 JSON：`d` 追加、`r` 整段替换、`x` 撤回草稿、`s` 本轮「折进来的」来源、最后 `{t:'final', payload}`；出错也走 final。响应头 `application/x-ndjson` + `no-transform`（防中间层为了压缩攒块）。
- **从半截 JSON 里取正文**：模型输出是一个 JSON 对象，读者要看的只有 `reply`。`lib/agent/replyStream.ts` 的 `partialReply` 逐字解码 `reply` 字符串（转义被分块截断时等下一块），`createReplyStreamer` 只发新增部分；末尾留 24 个字符不发，等后文到了再发。
- **草稿与最终回复同一组改写**：护栏对回复只做追加（⚠️ / 注：），不删改正文，所以先显示正文不会绕过它；追加的说明随完整结果到达。最终回复还会经过的确定性改写——引用标记 `[K3]`→`[n]`、编造条号改写、「实时」措辞、markdown 压平、去掉收尾的「办完了」——草稿也同样过一遍（`view`）。改写影响到已发出的文字时发 `r` 纠正。
- **一轮里的多次模型调用**：备用模型、解析失败后的重试、查数据后的第二次调用开始前都会撤回上一段草稿（查数据那种会先看到「我查一下」，再换成真正的答案）。
- **客户端**：`lib/agent/turnStream.ts` 解析事件流，对不流式的服务端同样可用（整个响应体当作 final）。`useAgentSession` 多了 `streamingText` / `streamingSources`，只是界面状态：不进消息列表、不存盘、不进下一轮的历史；切换对话时清掉，草稿只显示在提问所在的对话里。`AgentChat` 在原来「思考中」的位置显示草稿气泡，样式与正式消息相同；读者往上翻时不强制跟随。

**线上实测**（ship121 之后）

- 同一接口不带 `stream`：格式与原来一致，整段 7.1 秒（原来 10 秒以上）。

## 护栏误报：「以上操作尚未真正执行」加在了正确的回答后面（2026-11-17 夜 · 用户「修护栏误报」· ship126）

做流式回复时看到的：租客问「房东可以不提前通知就进我的房间吗」，回答完全正确，结尾却多了一句「注：以上提到的操作尚未真正执行…」。

**原因**：护栏 3b（`executed_claim_in_reply`）用 `EXECUTED_CLAIM` 直接匹配整段回复，只要出现「已…发出 / 提交 / 签署 / 申请 / 安排…」就认定助理在声称自己办了事，不看是谁做的。

**改法**（`lib/agent/guardrail.ts`，`replyClaimsExecution`）：先去掉引号里的文字，再逐句、逐分句判断。分句里有那类动词，而且不属于下面任何一种，才算助理在声称执行：
- 疑问（吗 / 是否 / 句末问号只管最后一个分句）；
- 条件与时间（如果 / 一旦 / 的话 / 情况下…；条件管它所在的分句和这句话后面的部分）；
- 建议与要求（请 / 确认 / 必须 / 可以 / 通常…；「申请」里的「请」不算）；
- 第三方或用户自己的动作（「房东已…」「双方已经…」「你已…」，或以这些人开头的分句）；
- 修饰语和时间点（「已签署的租约」「提交成功后」「付款完成前」）；
- 起草稿的引入句之后的正文（「内容如下：」「正文：」「你可以这样说：」之后是用户要发的话）——草稿里只有明确的「已帮你 / 替你…」仍然算。
第一人称（我）和「帮你 / 替你 / 为你」优先于后几条。英文同样处理。**卡片标题与摘要那条路径没动**：卡片永远是助理自己的话。动词表补了「发给」「邀请」，第三个模式的起始词加了单独的「已」（「已给房东发了消息」原来漏判）。

**验证**

**取舍**：这是把一条兜底规则收窄。漏判的代价是模型谎称办了事时少一句更正；误判的代价是每二十轮就在正确答案后面加一句让人以为答案有问题的话。系统提示词本身禁止模型声称已执行，卡片路径也没放松。草稿之后的正文里，不带「帮你 / 替你」的声称现在不会被拦，这是有意放掉的一种情况。

## 条号核对把正确的条号改掉了（2026-11-18 凌晨 · 用户「接着查」· ship128）

## 经纪对话里的「AI 起草回复」（2026-11-22 · 用户发 Sheng Chu 经纪主页截图「这里给经纪发消息的功能，是否可以有经纪的 Agent 来回答问题？」→「先做起草」· ship135）

**先回答的问题**：访客从经纪主页发消息，现在是记进经纪的客户表、开一条两人对话、通知经纪，之后全靠经纪本人回。能不能让经纪的 AI 来答，给了三种做法：
1. AI 以经纪名义自动回答——不建议：经纪要对以自己名义说出去的话负责，这要她和所属经纪公司的主管经纪点头；也和「经纪身份的模型不替人办事」「人与人的消息是只追加的留痕」两条既定规则冲突。
2. AI 起草、经纪确认后自己发——建议先做，用户选了这个。
3. 明确标注「我是某某的 AI 助理，不是经纪本人」的即时答复——留作第二步，需要经纪自己开启并得到经纪公司认可。没有做。

**做了什么**
- `POST /api/threads/draft-reply { thread_id, seed?, lang? }`。只给「经纪 ↔ 客户」对话（`agent_client`）里的经纪本人：对话和消息用调用者自己的 JWT 读（不是当事人读不到）；对话背后的客户行必须把调用者记为经纪（否则 403 `agent_only`，对话另一方也是当事人，所以要单独挡）；RECO 注册必须在有效期内。它只返回文字，不写任何消息、不发通知；审计只记一行 `thread_reply_drafted`（模型、知识库命中数、是否带了经纪已写的开头、草稿长度），不记正文。
- 送给模型的：最近 12 条人发的消息（不含系统行和正式通知副本，撤回的去掉，每条截到 1200 字）、经纪的公开资料（注册名、类别、经纪公司、语言、服务区域、专长、简介）、客户的名字（只取第一个词）、身份、区域、预算，以及针对客户最后一条消息检索到的知识库原文。不含邮箱、电话、附件。
- 提示词的规则（`lib/threads/replyDraft.ts`）：以经纪本人口吻、不提 AI；用对方的语言，三到六句；不编房源、地址、价格、带看时间、佣金，不评价市场；可以问推进所需的信息，不问也不评论人权法保护的事项、不问收入来源；法规只按参考资料回答，条号只用参考资料里的；不说已经做了什么；不作代表关系上的承诺；经纪已经写了开头就在它的基础上写完。输出 `{draft, notes}`，notes 是只给经纪看的提醒。
- 输出之后的处理：条号核对沿用助理那一套（`checkCitations` + `citationAllowance`）；确定性的两道提示——草稿像是问到了受保护事项、或对市场和房源多少下了判断，就在提醒里告诉经纪；客户表里没有 RECO Information Guide 的日期时另给一条提醒（来自客户行，不是模型说的）。

**实测后补的两处**（本机预览，经纪测试号对一条真实的测试对话）

## 服务商入驻页按「上门维修 / 专业服务」分开（2026-11-23 · 用户发入驻页截图「这个页面是否也要区分维修和专业服务？」· ship140）

**回答是要分。** 入驻页只有一张表：标题是「加入 Stayloop 精选维修网络」，说明里讲的是派单，12 个工种排成一排（8 个维修后面跟着摄影、保险经纪、Paralegal、律师），定价方式、时薪、上门费、「接单邮箱」对谁都出现，承诺条款写的是「接受工单即与房东直接订立服务合同」。一位律师来入驻，看到的全是给水管工写的话。目录早就是两个标签，入口这一页没跟上。

**做法**
- 表单最上面多一个二选一：**上门维修**（水管、电气、供暖、门锁、杂工等，核验后可以接到房东的派单）和**专业服务**（持牌 Paralegal、律师、保险经纪、房源摄影，只在目录里展示和转介、不派单）。选哪个，下面这些跟着换（规则和文案都在 `lib/marketplace/onboardKind.ts`）：
  - 标题与说明：专业服务是「加入 Stayloop 专业服务目录」，讲牌照、不派单、不收佣金、委托和费用双方直接谈。
  - 可选项目：只列这一类的（8 个工种 / 4 个服务类别）。
  - 定价：只有上门维修才问定价方式、时薪、上门费。派单报价要用到这些；专业服务不派单，持牌的也不在这里登记收费。
  - 几处用词：「商号（对房东显示）」→「对外显示的名称（事务所 / 工作室）」，「接单邮箱」→「联系邮箱」，「资质」→「牌照与资质」，简介的提示语。
  - 可登记的资质种类：只列这一类用得上的；专业服务把 LSO、RIBO 牌照排在前面。
  - 资质到期的后果、保存后的提醒、删除确认、页脚的声明：维修说的是派单会跳过你；专业服务说的是目录里会显示「牌照待核或已过期」，以及 Stayloop 不是律师事务所也不是保险经纪。
  - 承诺条款按**实际选了哪类项目**来拼：只有维修项目是原来那句，只有专业服务是「所列牌照由我本人或本所执业人员持有并处于有效状态…」，两类都有就两句都在。
