PROPOSAL · 待用户决定

三阶段可见化与三角色流程细化方案

调研头部租赁 / fintech / proptech 平台如何把多阶段流程做成页面上的功能；提出让「租前 · 租中 · 租后」在工作台里直接可见、可操作的做法，并逐角色细化流程。本文只给方案与决策点，不含实现。
2026-09-23 · 依据：各平台官网、帮助中心与设计系统公开资料（见文末来源）；Stayloop 现状取自当前代码库。
需要你决定的 6 件事（详见第 6 节）：① 阶段轨放在哪几个页面；② 房东端是否以「房源」为对象建管道看板；③ 经纪端流程是否改为「以客户为对象、无佣金结算」；④ 租客申请追踪器是否要「房东已查看」这一事件；⑤ 是否做「今日」视图；⑥ 分期与顺序（推荐 P0 → P1 → P2）。

0 · 一页结论

  • 头部平台的共同做法不是「更多功能」，而是「把阶段变成界面骨架」：TurboTenant 用 Leads → Applicants → Tenants 三栏管道、Avail 用单元为中心的一条仪表盘、Zillow 让租客看到「房东已打开你的申请」、Wise 用消费者语言的转账时间线、Stripe 把激活清单常驻侧栏、Airbnb 用「今日」按时间切片、GOV.UK 把「进度跟踪器」与「任务清单」「时间线」严格区分。
  • 我们功能齐全但阶段不可见：三阶段只出现在营销页；工作台里的 WORKFLOW_STAGES 是 V4 时代的对话阶段（由模型写 next_stage），与真实数据脱节，经纪版还含已冻结的「成交分成结算」。
  • 建议做三件事：P0 阶段轨（LifecycleRail）——每个工作台常驻一条 租前 · 租中 · 租后，阶段由数据库行推导，段内给下一步动作；P1 对象追踪器——租客每份申请、房东每套房源、经纪每位客户各自一条进度条与看板；P2 「今日」视图 + 三角色流程的新增能力（退租、入住清单、客户对象）。
  • 原则不变：阶段是确定性推导，不由模型判断；每个阶段的「下一步」要么链到真实页面，要么生成待批卡；示范内容不进阶段轨。

1 · 调研：平台怎样把多阶段做成页面功能

平台类型页面上的做法可借到 Stayloop 的点
TurboTenant租赁（美国小房东）仪表盘按阶段分栏：Leads → Applicants → Tenants；线索完成申请自动移到下一栏；每栏计数与实时提醒。房东端以「房源 / 申请人」为对象的阶段列；申请提交、筛查完成等事件自动推进，不用房东手动拖。
Avail（Realtor.com）租赁一个仪表盘串起 listing → screening → lease → rent → maintenance，以单元为中心；报修与费用同页可见。「单元视图」：一套房源从挂牌到在管在同一页接力，我们现在分散在 5 个页面。
Zillow Rental Manager租赁租客申请仪表盘可见「房东已打开你的申请」；状态变化邮件通知；Zillow 明说自己不参与录取决定。租客申请追踪器的「已查看」事件；「决定由房东本人作出」的边界写法与我们一致。
liv.rent租赁（加拿大）搜索 → 申请 → 数字合同 → 付租 → 续约全部在线；合同可在 verify.liv.rent 独立验证；付租提醒在合同生效后自动开启。「合同生效」作为阶段切换点自动开启租中能力（我们已有：双签自动建在管租约）；可验证合同链接我们已有永久签署链接。
SingleKey / Openroom租赁（加拿大）从 leads 到签约的线性引导；筛查报告 + 租金保障 + 判令数据；租客侧「已验证档案」可重复出示。租客护照的「一次验证、处处出示」我们已有；线性引导可作为阶段轨的段内步骤。
Stripefintech激活清单常驻仪表盘侧栏（验证邮箱 → 验证企业 → 开通支付），每项带完成态与进度条，全部完成才消失；空态即引导。常驻而不弹窗；阶段轨要像它一样一直在，直到该阶段完成；空态写「下一步做什么」。
Wisefintech转账时间线：处理中 → 已收到 → 已发出 → 到账，附预计时间；界面用消费者语言，不用 API 状态名。追踪器每步给预计时间（申请通常 1–3 天、筛查几分钟、租约签署等待对方）；状态用人话不用表字段名。
Wealthsimplefintech（加拿大）分钟级开户，进度指示 + 每步内联提示；用 Flinks 连接银行一步完成。租客「护照就绪」与申请人核验用同一进度语言；Flinks 我们已接。
Biltproptech / fintech按时付租 → 积分 / 上报信用；「如果历史租金早上报，你的分数会是多少」的预估。租后阶段给租客一个看得见的收益：租史进护照、未来上报信用局；让「租后」不是空段。
Airbnb Hostproptech「Today」tab 按时间切片：即将到达 / 入住中 / 退房 / 待回复请求（带 24 小时倒计时与接受 / 拒绝按钮）。「今日」视图：待批卡、今天到期的租金、今天的看房、N1 截止日倒计时。
Doorstead / Belongproptech（全托）业主门户按阶段推进：报价 → 签约 → 验房 → 挂牌 → 筛查 → 保障时钟开始；固定日付款。阶段切换有明确「时钟」：我们的续约窗口（到期前 120 天）、N1 截止日、N4 7 天都是可显示的时钟。
GOV.UK / MoJ 设计系统公共设计系统「进度跟踪器」= 固定有限步骤、每步完成 / 未完成、步骤可乱序完成但顺序固定；明确区别于「任务清单」（会增长）与「时间线」（记历史）。三个组件分开做：阶段轨（固定三段）、待办（任务清单，已有）、审计 / 活动日志（时间线，已有）——不要混成一个。
五条可迁移原则：① 阶段是界面骨架，常驻不弹窗；② 以对象为中心（申请 / 房源 / 客户），不是以功能为中心；③ 事件自动推进阶段，人只处理需要批准的事；④ 每步用消费者语言 + 预计时间 / 截止时钟；⑤ 进度跟踪器、任务清单、时间线是三种组件，各司其职。

2 · 现状诊断：阶段为什么看不见

现状问题
三阶段只在 /platform 与首页登录后没有任何页面显示「你现在在租前 / 租中 / 租后的哪一步」。
WORKFLOW_STAGES（orchestrator.ts）租客 6 步 / 房东 5 步 / 经纪 4 步是 V4 的对话阶段，由模型返回 next_stage 写入，不看数据库；经纪版含「接入转介」「成交分成结算」——与已冻结的佣金决策冲突。
StatusOverview 活数据瓦片数字是真的（待审申请、活跃租约、续约窗口…），但无序、不表达先后与下一步。
申请人列表按评分分组房东看到的是「推荐审批 / 需面谈 / 不推荐」（评分口径），不是「筛查中 → 已决定 → 租约已发」（阶段口径）。
租客「我的申请」只有状态徽章（已提交 / 已录取），没有追踪器，也没有「房东已查看」「筛查完成」等中间事件。
房源没有阶段字段房源只有 is_active / verification_status；「有申请 / 已录取 / 租约已签 / 在管 / 续约中 / 空置」要从五张表推。
租约结束在管租约到期后不会自动回到「租前」（重新挂牌），阶段没有闭环。

3 · 方案：让三阶段在页面上可见、可操作

3.1 P0 阶段轨 LifecycleRail（每个工作台常驻）

一条固定三段的轨：租前 · 租中 · 租后。每段显示：当前子步骤、完成态、一个「下一步」按钮（链到真实页面或直接生成待批卡）、一个时钟（如「N1 最晚 10-03」「租约 87 天后到期」）。阶段由规则表从数据库行推导，模型不参与。桌面端放工作台顶部（侧栏下方内容区第一行），手机端放助手页头像状态行之下（可折叠为一行 chip）与进度页顶部。

4.3 经纪（Brief）

现状的四个阶段（接入转介 → 任务收件箱 → 带看 → 成交分成结算）来自 V4 设想，与 2026-09-13 的决定（Stayloop 不做经纪业务、不收佣金、转介引擎冻结）冲突。建议改为以客户为对象的流程，每位客户一条追踪器，佣金结算彻底移出产品：

段步骤说明需要新增
租前1 客户接入：记录代表协议 + RECO Information Guide 已交付TRESA 要求；目前只有 s.32 披露记录agent_clients 表（客户、身份：租客侧 / 房东侧、协议日期）（P2）
2 租客侧：对话找房 / 挂牌定价（房东侧）已有（同一条找房与行情管线）—
3 带看准备包已有对话能力—
4 申请与筛查交接（费用由经纪 / 房东承担）已有规则客户视角的申请追踪（P2）
租中5 签约（标准租约 + Form 400 只作要约）已有事实包—
租后6 归档：客户成交记录 → 下一次转介只是「介绍」不是分成无佣金把「佣金 / 收益」页改为「客户记录」（P2）
经纪端决策点：「客户」表要不要做，取决于是否准备让经纪在平台上真的带客户走流程；不做的话，经纪端保持现在的「对话 + 认证 + 目录」三件事，阶段轨只显示认证状态与当前对话的客户。
