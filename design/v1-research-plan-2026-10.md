# V1.0 正式版 · 调研方案（2026-10-13，待用户确认后执行）

用户给的三个方向：① 重点先放在**给租客和经纪的工具**；② 如何**更好地服务房东和经纪**；③ **强化 API**，开放给其他 AI 和网站。
本方案只定「查什么、怎么查、产出什么、什么由你拍板」，不含任何代码改动。确认后按下面四条线并行执行，约 5 个工作日出齐全部调研稿，再汇成一份 V1.0 范围与路线图。

## 1. 调研线 A · 租客工具

**要回答的问题**：没有房源数据的前提下，租客为什么要打开 Stayloop？哪几件事是它能比别处做得更好、而且合法免费（RTA s.134 不得向租客收费）的？

- **A1 对标 8 个产品**（只看租客侧）：Rentals.ca、liv.rent、Zumper、Openroom（租客端）、RentCafe、Avail（tenant）、Rent Panda、以及一个纯 AI 产品（ChatGPT / Gemini 直接问租房问题）。
  每个记录：注册流程、申请包 / 租客档案、看房约定、租约解释、报修、续约 / 退租、争议、是否收费、是否有 AI。**实测截图存 `design/research/tenant/`**，不凭印象写。
- **A2 走查我们自己的租客链路**（muse-tenant 号）：从「问一句」到申请、签约、报修、续约，逐步记录卡住的地方与空页面。
- **A3 租客真正会付出时间的三件事做深度分析**：① 申请材料包 / 护照（现在是示范数据为主）——能否变成「一次准备、多次复用的申请包」，并与 CRA 注册状态解耦；② 租约解读与权利（RTA / 各省规则已内置）——做成租客问得最多的 20 个问题的实测准确率；③ 入住后的报修 / 续约 / 退租（已有执行器）——补什么才算闭环。
- **A4 法规边界**：租客侧哪些事不能做（代收租、向租客收费、替租客做法律代理），逐条附法条。

**产出**：`design/research/tenant-tools-2026-10.md`——对标表、我们的缺口清单（按「租客会不会因此回来」排序）、每项的工作量与法规门槛。

## 2. 调研线 B · 经纪工具

**要回答的问题**：安省租赁经纪一天在做什么、用什么工具、愿意为什么付费；Stayloop 在 RECO / TRESA 边界内能替他们省掉哪些重复劳动。

- **B1 工作流还原**：以 TRESA 义务为骨架（Information Guide → 代表协议 → 多重代表披露 → 挂牌 / 找房 → 带看 → 申请与筛查 → 要约（OREA Form 400）→ 标准租约 → 交接），每一步写清楚现在经纪用什么（邮件、WhatsApp、OREA 表单、经纪公司系统），以及我们现有功能覆盖到哪（客户表、委托、代客筛查、带看准备包）。
- **B2 对标 5 个经纪端工具**：Follow Up Boss、kvCORE / Lofty、OREA WEBForms、Zumper Pro / liv.rent agent、以及经纪常用的 ChatGPT 用法。记录定价与核心功能。
- **B3 访谈一位真实经纪**（建议 Sheng Chu，已有联系）：30 分钟，固定 12 个问题（每周租赁单量、最花时间的三件事、现在用的工具与费用、对 AI 的顾虑、是否会为筛查 / 客户管理付费）。**由你决定是否安排**。
- **B4 法规边界**：平台能否生成要约 / 租约给经纪用、能否代发通知、经纪付费档（$29 / $59）在 TRESA 下的披露要求，逐条附法条。

**产出**：`design/research/agent-tools-2026-10.md`——工作流覆盖图、缺口清单、经纪付费档的功能定义草案。

## 3. 调研线 C · 更好地服务房东（与经纪共用的部分）

**要回答的问题**：239 份筛查之后，房东为什么没有留下来做租约、报修、续约？哪一步最先掉人？

- **C1 漏斗实数**：从生产库算 注册 → 发布 / 筛查 → 申请 → 租约 → 在管租约 → 续约 的转化与时间间隔（只用真实账号，排除测试号）；审计事件里房东最后一次操作停在哪一页。
- **C2 对标 6 个房东工具**：TurboTenant、Avail、RentRedi、SingleKey、Openroom（房东端）、Rent Panda。重点看：收租方式与费用、租约起草、LTB 表格、报修、税务（T776）、定价。
- **C3 两个需要你拍板的方向做可行性**：① **在线收租**（我们一直「不经手资金」；研究 Stripe / Interac 预授权借记 / 第三方代收的合规与成本，给出做 / 不做的依据）；② **LTB 表格一键生成**（N4 / N1 / N12 / L1 等，官方 PDF 可填，法律上只能「填表」不能「送达」）。
- **C4 与经纪的交接**：房东委托经纪挂牌、经纪代客筛查已有；补「房东找经纪 → 经纪挂到 MLS → 我们只记 MLS 号」这一步需要什么。

**产出**：`design/research/landlord-retention-2026-10.md`——漏斗数据、掉点、对标表、两个拍板项的利弊表。

## 4. 调研线 D · 开放 API 与对其他 AI 的接口

**要回答的问题**：别的 AI（ChatGPT、Claude、Gemini、国内模型）和网站接进来能做什么、我们有什么可合法开放、怎么收费与限流。

- **D1 能开放什么（按法律与数据来源分三档）**：
  - 可直接开放：安省 + 12 省租赁规则与合规检查（`lib/ontario/rules.ts`、`lib/provinces/`，确定性、我们自己的）、CMHC / 统计局租金基准（开放授权，必须带来源句）、房源发布与我们自己的房源读写（房东授权）、租约 / 通知草稿生成。
  - 需用户本人授权：护照 / 核验快照（已有 s.8(1)(b) 模式）、租客自己的申请与租约、消息线程。
  - CRA 注册前不开放：按姓名查 LTB / 法院记录、筛查评分给第三方（现有 `/v1/screen` 需重新评估是否只对已绑定房东开放）。
- **D2 接入形态**：① REST + OpenAPI 3.1 文档（现有三端点重写）；② **MCP 服务器**（Model Context Protocol，Claude / ChatGPT / Cursor 等都能直接挂载——研究其鉴权、工具定义、托管方式）；③ ChatGPT Apps / Gemini Extensions 的提交要求；④ Webhook（事件推送）。每种记录鉴权方式、审核要求、维护成本。
- **D3 对标 4 家开放 API 的同类产品**：SingleKey API、Rentsync API、Openroom（若有）、以及一个非房产的「规则 / 合规 API」范例（如税率 API）的定价与文档结构。
- **D4 商业与风险**：密钥发放与配额、按次计费还是订阅、第三方 AI 误用我们数据的责任边界、PIPEDA 下第三方调用的同意记录、滥用检测。
- **D5 原型验证**：用现有 `listings/compliance` 端点在 Claude 桌面端挂一个最小 MCP 服务器跑通一次，记录工作量。

**产出**：`design/research/open-api-2026-10.md`——可开放清单（三档）、接入形态对比、定价与限流草案、MCP 原型结果。

## 5. 方法与规矩（四条线共用）

- **先实测再写**：对标产品要真实注册 / 走一遍，截图与原话存档；法规只引官方来源并附引文（与 10-02 外省法规研究同一标准）。
- **只用真实数据**：漏斗与用量从生产库算，排除 `[TEST]` / `test_account` / `muse_account`。
- **每条发现四个字段**：现状 · 证据 · 建议 · 门槛（法规 / 数据 / 工作量）。不写「即将」「业界领先」之类没有证据的话。
- **分工**：四条线各一个调研员并行，另一人做法规核查（A4 / B4 / C3 / D1 的法条逐条对照原文）；我做汇总与取舍。
- **不做**：任何 MLS / DDF / Realtor.ca 数据路径；向租客收费的功能；注册前的 CRA 受限功能。
